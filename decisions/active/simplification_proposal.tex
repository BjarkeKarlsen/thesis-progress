\section{Embed each window once}

This is the design in \file{embed\_once\_design.md}, now issue \#160. It is a
memory and scaling change and does not simplify the thesis. The text already
says the forward pass takes all agents of a timestep together and that a message
is the sender's embedding, so no sentence changes. It applies to the decentralised
arm with communication, the only arm with senders. In the code the net effect is
roughly neutral. It removes the six sender window keys and their padding, and it
adds keys, a lookup, a two-pass value computation and a minibatch iterator built
from whole timesteps. The message cap \texttt{max\_messages} appears 98 times
across 16 files and could become the fleet size.

\section{The factor-grid lever}\label{sec:grid}

You agreed with this. Run the main comparison of storage rule against architecture
at one congestion setting and one load, and treat congestion sensitivity and load
as separate one-factor sweeps.

\begin{itemize}[noitemsep]
  \item The main grid is $3 \times 3 = 9$ conditions.
  \item Fully crossed with load at 3 levels (my assumption, the thesis says
    several) the design is $24 \times 3 = 72$ conditions. With sweeps it is about
    18 to 24, depending on how many storage rules the load sweep repeats.
\end{itemize}

\textbf{The limit.} RQ4 asks how the \emph{effects} change with load. The effect of
coupling is adaptive against fixed storage, and it differs by architecture, so the
load sweep must repeat that comparison for every architecture. It cannot run at one
storage rule. RQ3 needs congestion sensitivity switched on and off in both the
storage and the routing layer, so the congestion sweep needs the routing toggle for
each architecture as well. One-factor sweeps also lose interactions, such as whether
congestion sensitivity matters more under high load.

\textbf{Verdict.} The largest single saving in conditions, and in the text that
explains them. It is a change of design, and a conversation with the supervisor is
worth having.

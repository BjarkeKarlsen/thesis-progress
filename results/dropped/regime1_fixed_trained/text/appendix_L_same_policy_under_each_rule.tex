Each controller's policy trained under fixed storage was also played under congestion-aware storage. The
policy stays the same, so any change comes from the storage rule alone. The test is the same as
above, 20 seeds of 10000 steps with the first 5000 left out. Under demand storage these policies were
played only before the served share was counted, so that rule is left out here.

The storage rule on its own changes nothing the test can measure (Table~\ref{tab:app:regime1:16}).
Under congestion-aware storage the centralised policy finishes 0.143 tasks per step, the same as
under fixed storage. The decentralised policy finishes 0.028 against 0.025. Compared seed by seed,
the 95\,\% interval holds zero for both, and the rule does better on only 9 and 10 of the 20 seeds.
No run keeps up under either rule.

The better congestion-aware rows of Section~\ref{app:results:tests:16} come from the training run,
not from storage. Under the same rule, the decentralised policy trained under congestion-aware
storage finishes 0.186 tasks per step, and the one trained under fixed storage 0.028. For the
centralised controller it is 0.161 against 0.143. Both do better on all 20 seeds. Each controller has one training
run per rule, so this cannot tell training under the rule apart from a better training run. The
decentralised run trained under fixed storage was already weak in validation, at 0.088 tasks per step % validation rows use the old count
against 0.210.

The decentralised policy trained under fixed storage serves only about an eighth of the work under
either rule, so the rule has little to work on there.

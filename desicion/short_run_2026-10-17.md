# Short run, 2026-10-17

What the short validation run of 2026-10-17 measured. Run folder:
`~/thesis_runs/short_2026-10-17/` (`run_short.sh`, `STATUS.md`, `short.log`, `summary.md`,
`runs/`, `logs/`). Code `slap-mapd-coupling` `main` at `9b6be93` (PR D and PR E merged).

**Main point. None of the four learned arms trained.** All eight training attempts (four arms,
two attempts each) stopped about 3 seconds after starting, before the first iteration, because
Ray could not create its sockets. Only the Token Passing reference ran. So RQ2, the comparison
of the controllers and the training questions have no data from this run. RQ1 and RQ3 have an
answer for Token Passing only. The run has to be repeated after a one-line fix (below).

- 100 SKUs, 8 units each, Zipf demand with skew 1, the ranking rotates by 5 places every 200
  steps, starting stock in blocks (`configs/medium/*.yaml`).
- Four learned arms (decentralised, centralised, section, full view), training seed 0,
  140 000 timesteps (10 iterations of 7 runners x 2000 steps), fixed storage, load 0.6.
- Measurement: checkpoint chosen on 2 validation seeds, then the chosen and the last checkpoint
  on 6 test seeds (200 000 to 200 005), under fixed, demand and congestion storage (Δ 100,
  ν 48, β 3), at load 0.6 and 0.3.
- Token Passing on the same test seeds, rules and loads (`tp_reference.py`).

## Why training failed

Every `logs/<arm>_seed0_train.log` ends in the same error, raised by `ray.init()`:

```
OSError: validate_socket_filename failed: AF_UNIX path length cannot exceed 107 bytes:
/home/bjarkek/thesis_runs/short_2026-10-17/ray_tmp/ray/session_2026-10-17_14-47-10_046997_427505/sockets/plasma_store
```

That path is 117 bytes. `run_short.sh` sets `RAY_TMPDIR="$HERE/ray_tmp"`, a 50-character
directory, so that Ray's session logs do not fill the 16 GB RAM disk at `/tmp`. Ray appends
about 67 characters to it (`/ray/session_<date>_<time>_<µs>_<pid>/sockets/plasma_store`), so
`RAY_TMPDIR` can be at most about 39 characters. The night run of 2026-10-16 used the default
`/tmp` and did not hit this. The error is deterministic, so the second attempt of each arm
could not succeed either.

Two smaller faults in the run scripts made the failure easy to miss.
- `run_short.sh` ends with "short run finished, results in summary.md" even when no arm
  trained, because the summary step only fails if `summarise.py` itself fails.
- `summarise.py` silently leaves out an arm with no `test.jsonl`. `summary.md` reads as a
  complete result with only the Token Passing rows in it.

## Measured, Token Passing only

Mean ± standard deviation over the 6 test seeds. Gains are paired seed by seed. "6/6" counts
the seeds where the paired difference has the stated sign. The 95% intervals use the t
distribution with 5 degrees of freedom.

### RQ1, adaptive storage against fixed

**Load 0.6.** No storage rule keeps up (keep-up ratio 0.61 to 0.75, threshold 0.8), so only
throughput and backlog are compared.

| storage | throughput | gain over fixed | backlog at T | change in backlog |
|---|---|---|---|---|
| fixed | 0.375 ± 0.005 | | 457 ± 22 | |
| demand | 0.428 ± 0.011 | +0.053 ± 0.011, 95% [0.042, 0.065], 6/6 | 350 ± 28 | −107 ± 23 |
| congestion (β 3) | 0.421 ± 0.007 | +0.046 ± 0.006, 95% [0.039, 0.052], 6/6 | 365 ± 23 | −92 ± 13 |

The demand rule finishes 14% more tasks than fixed storage.

**Load 0.3.** Every run keeps up (keep-up ratio 0.83 to 0.94), so service time counts.

| storage | service time | gain over fixed | wait for agent | travel | blocked | crowding |
|---|---|---|---|---|---|---|
| fixed | 52.2 ± 11.6 | | 39.2 ± 11.5 | 12.9 ± 0.2 | 0.20 ± 0.02 | 0.096 |
| demand | 39.2 ± 6.1 | 13.0 ± 7.8, 95% [4.8, 21.2], 6/6 | 27.7 ± 5.9 | 11.2 ± 0.3 | 0.32 ± 0.07 | 0.099 |
| congestion (β 3) | 43.1 ± 9.4 | 9.2 ± 4.4, 95% [4.6, 13.8], 6/6 | 31.1 ± 9.1 | 11.7 ± 0.3 | 0.26 ± 0.04 | 0.098 |

Paired changes against fixed storage, by part of service time.

| part | demand | congestion |
|---|---|---|
| wait for agent | −11.5 ± 7.8, 6/6 lower | −8.1 ± 4.5, 6/6 lower |

The demand rule cuts service time by 25%. Travel drops on every seed (−13%), but nine tenths
of the gain sits in the wait for an agent. Blocked time rises on every seed, from a small
base. Throughput rises by +0.014 ± 0.003 (6/6), and the backlog at T halves (56 to 29).

The congestion rule does what it is built for, less blocking and less crowding than the demand

but no run keeps up there, so that average covers a different set of finished tasks and is not
a result.

### Cost of adaptive storage

| | load 0.6, demand | load 0.6, congestion | load 0.3, demand | load 0.3, congestion |
|---|---|---|---|---|
| units relocated per update | 48 | 48 | 48 | 48 |
| relocation distance per update | 365 ± 17 | 274 ± 23 | 256 ± 10 | 262 ± 12 |
| distance per relocated unit | 7.6 | 5.7 | 5.3 | 5.4 |
| tasks finished per update (100 steps) | 42.8 | 42.1 | 27.4 | 27.0 |
| task travel per update (tasks x mean travel) | 379 | 383 | 306 | 316 |
| relocation distance / task travel | 0.96 | 0.71 | 0.84 | 0.83 |

Every update moves 48 units, more than the 27 to 43 tasks the fleet finishes in the same 100
steps. Over one episode the rule moves 960 units, more than the whole starting stock of 800.

Token Passing decides in 0.77 ms per decision at load 0.6 and 0.39 ms at load 0.3, the same
under every storage rule.

## Inferred, not measured

- **RQ1 for Token Passing is a clear yes.** Both adaptive rules beat fixed storage on every seed
  at both loads, and the intervals exclude zero. This repeats the probe on two more seeds.
- **At load 0.3 the gain is mostly a queueing effect.** Travel falls by 1.7 steps per task, yet
  service time falls by 13. Token Passing finishes 0.83 to 0.90 of the arriving tasks under fixed
  storage, close to its limit, so a small saving in travel per task shortens the queue for an
  agent by much more. The thesis expects adaptive storage to show in travel
  (`sec:pf:measures`). It does, but the size of the gain in service time depends on how close
  the fleet runs to its limit. At a lower load, where waiting for an agent is small, the gain
  would be close to the travel saving alone. This matters for RQ2, because arms that finish
  tasks at different rates sit at different distances from their limit at the same load.
- **Popular stock near the delivery vertices adds a little blocking.** Both rules raise blocked
  time on every seed. The rise is small for Token Passing (0.2 to 0.3 steps per task), which
  plans conflict free. For a learned arm that blocks more, the same concentration could cost
  more, and that is where the congestion rule could pay off.
- **RQ3 at β 3, for Token Passing, says no.** The congestion rule trades blocked time for
  travel, and travel costs more. This agrees with the probe, which found today's score helped
  only at β 1 and only for the decentralised policies. β 3 is the wrong test value for the
  long run if β 1 is the candidate.
- **The relocation cost is of the same order as the fleet's own travel.** If the robots
  carried the relocated units one per trip, the distance alone would be 0.7 to 1.0 times the
  travel the tasks need, so the 14% throughput gain at load 0.6 would likely vanish. The
  comparison is rough, since relocation distance is in edge cost and travel in timesteps. ν = 48
  binds at every update, and the probe found ν = 16 gives a smaller gain (+0.034 against
  +0.057). The gain against the relocation cost is a curve in ν, and one point of it does not
  show whether adaptive storage pays.

## Limits

Token Passing only, one instance, 6 test seeds, one setting of the storage rules (Δ 100, ν 48,
β 3). The Token Passing rows are deterministic given the seed, so they carry no training-seed
variation. For the learned arms the planned run would have had one training seed and 10
iterations, which is far from trained.

## Before the run is repeated

1. **Shorten `RAY_TMPDIR`** in `run_short.sh` to a directory on disk of at most about 39
   characters, for example `/var/tmp/ray_short` (on the 200 GB main disk, 87-byte socket path).
   Clear it after the run, since Ray session logs pile up there.
2. **Make a failed arm visible.** `run_short.sh` should end with "finished, N of 4 arms
   trained" and a non-zero exit when any arm is missing. `summarise.py` should list missing
   arms at the top of `summary.md`.
3. **Do not retry a failure that took seconds.** A second attempt helps against a crash late in
   training, not against a setup error. Retry only when the first attempt got past iteration 1.
4. **Smoke test before the full run.** One arm, 1 iteration, the exact `run_short.sh`
   environment. It would have caught this in under a minute.
5. Remove the four `*_failed_*` folders and the empty `<arm>_seed0` folders before starting
   again (the script moves the latter aside itself). They hold only a spec, an empty progress
   file and a `tuner.pkl`.
6. Nothing else in the code or config needs to change for the repeat. The Token Passing rows
   show that the storage code and config match the probe.
